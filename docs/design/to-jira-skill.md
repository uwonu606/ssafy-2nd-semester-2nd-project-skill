# `/to-jira` 스킬 — 설계 합의

설계 문서를 읽어 Jira에 **하위 작업**을 등록하는 스킬. 2026-09-01 그릴링 합의.

---

## 1. 무엇을 만드나

```
/to-jira docs/design/pipeline-core.md
```

문서를 태스크로 전부 쪼개고 → 기존 스토리에 매핑하고 → 사람이 확인한 뒤 → Jira에 등록한다.

**bottom-up이다.** 문서 목차를 따라 내려가지 않고, 해야 할 일을 먼저 다 쪼갠 다음 그것들을 스토리로 묶는다.

---

## 2. 환경 — 실행할 때 읽는다, 박아두지 않는다

아래는 2026-09-01 조사 결과다. **스킬에 하드코딩하지 않는다.** 스킬에 적는 건 *어디를 봐야 하는지*지 *무엇이 있는지*가 아니다.

|---|---|
| 사이트 | `ssafy.atlassian.net` (Confluence 없음 — 위키 API 404) |
| 프로젝트 | `S15P21A102`, 보드 15404 |
| 이슈 타입 | 에픽(1) · 스토리·작업·버그(0) · **하위 작업(-1)** |
| 실제 쓰는 계층 | **에픽 > 스토리 > 하위 작업.** `작업` 타입은 0건 |
| 에픽 | 8개, `이모지 + ~ 시스템` (`👗 패션 시스템` = `-80`) |

| 이슈 링크 | **0건** — 아무도 안 쓴다 |

## 3. 계층 권한

| 층 | 스킬이 | 왜 |
|---|---|---|
| **에픽** | **절대 안 만든다.** 기존 것 중에서 고른다 | 8개가 제품 전체를 덮는 고정 골격. 새로 만든 에픽은 골격에 흡수됐다(`-80` 사건) |
| **스토리** | 기존 것에 붙이는 게 기본. 안 덮이면 새로 제안하고 **승인**받는다 | |
| **하위 작업** | 자유롭게 만든다 | |

**에픽 질문은 새 스토리를 만들 때만 생긴다.** 기존 스토리에 붙으면 에픽은 그 스토리의 부모로 이미 정해져 있다.

**하위 작업은 부모 없이 못 만든다**(Jira 필수 필드). 따라서 순서가 강제된다 — 태스크 **초안**을 다 뽑고 → 스토리를 정하고 → 그때 한꺼번에 생성. **등록 직전까지 Jira에 아무것도 안 닿는다.** 중간에 그만둬도 반쯤 만들어진 이슈가 안 남는다.

## 4. 흐름

```
문서 읽기
  ↓
태스크 초안 전량 (§5 경계 규칙)
  ↓
기존 스토리 24개에 매핑 · 안 붙는 것만 새 스토리 제안
  ↓
매핑표 한 장으로 전량 제시  ←── 여기서 사람이 자유 수정
  ↓
⚠️ 진짜 갈림길만 AskUserQuestion (회당 4문항, 한두 번)
  ↓
Jira 등록 (의존 순서대로)
```

**매핑표를 한 장으로 내는 이유**: 태스크마다 물으면 25~40번 묻게 되고, 그러면 사람이 전체를 못 본 채 하나씩 판정한다. "이거 너무 잘게 쪼갰는데"를 알아채는 순간이 영영 안 온다. AskUserQuestion은 선택지를 좁히는 도구라 ⚠️ 갈림길에만 쓴다.

매핑표 아래에 **점검 흔적** 구역을 붙인다.

```
쪼갠 것        크롤러 / 매칭기 / 추출기 → 3건 · 테이블 경계
합친 것        입력 조립·출력 검증·배치 제출 → [DATA] 추출기 구현 1건 · 한 부품의 내부 단계
               크롤러 공통 기반 + 어댑터 4종 → 1건 · 서로 있어야 검증되는 양방향 의존
               저장 접속 계층 → 크롤러에 흡수 · 행동 없는 공통 층은 첫 소비자 몫
흡수한 실행     3개월 백필 → 크롤러 완료 기준 · 브랜치가 없다
방법으로 뺀 것   발굴기 공통 어댑터 · mine() 시그니처 · 어댑터 4종 분류 · Aho-Corasick → 문서 서술의 한 방법. 수행자 몫
⚠️ 갈림길      어댑터를 크롤러에 합칠지 따로 둘지 · 사람이 나눠 맡을지에 달렸다
```

**이 구역이 비어 있으면 점검을 안 한 것이다.** 합친 것이 0건이면 구현 분해도를 그대로 옮긴 것이고, 방법으로 뺀 것이 0건이면 문서 서술을 그대로 옮긴 것이고, 흡수한 실행이 0건이면 문서에 실행 단계가 없었는지 다시 본다. (2026-09-02 재단 이전 예시는 §14.)

## 5. 태스크 경계 — 브랜치 하나 = 부품 하나

**2026-09-02 재단.** 첫 등록(39건)이 구현 분해도가 돼 버려서 규칙을 바꿨다. 경위는 §14.

**태스크 하나 = 브랜치 하나 = 부품 하나.** 부품은 다른 부품과 **저장된 산출물(테이블)이나 인터페이스로만** 통신하는 덩어리다. `pipeline-core.md` §2 단계 경계와 §4 seam 이 그대로 부품 경계다. 부품 안의 내부 단계(입력 조립·출력 파싱·저장·버전 산출)는 나누지 않는다 — 그건 구현 분해도이고, 구현은 구현할 때 고민한다.

태스크마다 **완료 기준 한 줄**이 서야 하고, 그 한 줄은 "부품이 돌아간다"를 말한다. 판정에 다른 태스크가 필요 없어야 하고(입력은 고정 자료로 대신한다), 코드가 판정한다.

### 나누는 신호 둘, 합치는 신호 셋

| 나누는 신호 | 예 |
|---|---|
| 테이블·인터페이스 경계를 넘는다 | 매칭기 → `mention` → 추출기 |
| 같은 인터페이스의 구현체가 여럿이라 사람이 나눠 맡을 수 있다 | 매체 어댑터 4종. 몇 건으로 묶을지는 사람이 정한다 — ⚠️ |

| 합치는 신호 | 예 |
|---|---|
| 한 부품의 내부 단계 | 입력 조립 · 출력 검증 · 배치 제출 → 추출기 하나 |
| 한 부품의 부속 규칙 | 표면형 등록 규칙 → 사전 도구 |
| 코드가 없는 실행 | 3개월 백필 → 그 결과를 내는 부품의 완료 기준에 흡수 |
| 공통 기반과 구현체가 서로 있어야 검증된다 | 크롤러 공통 기반 + 어댑터 4종 → 한 브랜치. 인터페이스는 구현체를 보고 굳힌다 |
| 행동이 없는 공통 층 | 저장 접속·설정 → 첫 소비자 브랜치가 만든다. 테이블은 그 테이블에 처음 쓰는 부품 몫 |
| 오케스트레이터가 맡는 것 | 스케줄·재시도·대기가 Airflow 몫이면 "서버화" 부품은 없다. 각 부품이 자기 DAG 를 갖는다 |

**접속사는 신호가 아니다.** 옛 규칙의 "접속사로 판정이 둘이면 나눈다"가 39건을 만든 원인이다. "조립하고 검증한다"는 한 부품의 두 단계다. 접속사가 갈라놓는 두 쪽이 서로 다른 부품일 때만 나눈다.

**크기는 기존 하위 작업과 견준다.** 이 팀의 기존 하위 작업 하나(`-8 크롤러 구현`, `-12 DB 스키마 구축`, `-20 조회 API`)가 브랜치 하나다. 그보다 눈에 띄게 잘면 함수를 세고 있는 것이다.

**부품 수는 문서의 단계 수 + seam 수 근처다.** `pipeline-core.md` 는 단계 5 + seam 5 = 10 인데 첫 실행이 39 를 뽑았다. 두 배 규칙이면 그때 걸렸다.

시간 추정은 여전히 안 쓴다 — 이 팀은 스토리 포인트를 안 쓰고, 문서만 읽는 스킬이 "1.5일"이라 적으면 그건 지어낸 숫자다.

### 따라붙는 규칙 둘

**품질은 완료 기준이 아니다.** "사전이 충분한가", "추출이 정확한가"는 태스크에 안 쓴다. `pipeline-core.md` §7 검증 4층이 그 층을 이미 갖고 있다. 태스크에 끌어오면 닫을 수 없는 이슈가 된다. 태스크 완료는 **만들어졌나**까지다.

**조사는 독립 태스크로 안 뗀다.** 조사만 떼면 완료 기준이 "알아냈다"가 되어 코드가 안 붙는다. 그 조사가 필요한 부품에 흡수시키고 "조사 결과를 이슈에 남긴다"를 경계에 적는다.

### 코드로 안 넘어오는 것은 스토리로 올린다

`pipeline-core.md` §12: *"랭킹을 눈으로 보고 '이것이 트렌드로 보이는가'를 판단 ← 이 시점에 자동 게이트는 없다. 사람이 보는 것이 유일한 관문이다."*

태스크는 "랭킹 3종이 `weekly_score`에 산출된다"에서 코드로 닫고, **사람 판단은 그 태스크들을 묶는 스토리의 완료 조건**으로 올린다. 태스크는 전부 코드 판정이라는 규칙이 서고, 사람 판단은 사라지지 않고 한 층 위에 남는다.

새로 만드는 스토리에만 쓴다. **기존 스토리 24개는 안 건드린다.**

## 6. 이슈 본문

### 자족성 — 얼마나 옮길지를 정하는 기준

**팀원은 설계 문서를 안 본다. Jira만 본다.** 따라서 이 이슈만 읽고 **무엇을 지켜야 하는지**를 알 수 있어야 한다. 단, **어떻게 만드는지**는 넣지 않는다 (2026-09-02, §14).

> 수행자가 문서를 못 본다고 치고, 이 이슈만으로 *틀린 방향으로 가지 않고* 일을 시작할 수 있나?

*없으면 틀린 방향으로 가는 것*(불변식·seam 계약·잠정값)은 넣고, *구현 때 정하면 되는 것*(컬럼 초안·사이트맵 경로·알고리즘)은 뺀다. §12식 전량 복사도 아니고 절 번호만 남기기도 아니다.

**문서 참조는 이슈에 안 남긴다.** 로컬 매핑 파일도 안 만든다. 대신 **라벨을 반드시 건다** — 이 문서에서 나온 이슈를 찾는 유일한 끈이다. `-80`이 스토리 9개가 지워지는 와중에 `trend-keyword-pipeline` 라벨을 달고 살아남은 것이 근거다.

바뀔 값들은 어차피 경계 줄에 복사돼 있어서, §5의 리드 길이가 300→500으로 바뀌면 `text ~ "300자"`로 찾을 수 있다. 절 번호가 하던 일을 값 자체가 한다.

### 하위 작업 템플릿

```
[DATA] 추출기 구현 — 프롬프트 계약·배치·extractor_ver, 3개월 전량 추출 포함

왜   집계가 extraction 을, 유지보수가 new_candidate 를 읽는다.
     모델이 생성하지 않고 선택하게 만드는 지점이다.

완료 기준
  3개월 is_fashion=1 기사 전량에 extraction 행이 있고 실비용이 기록되며,
  범위 밖 인덱스와 본문에 없는 new 는 코드가 버린다.

경계
  · 모델 입력은 제목 + 리드 300자(잠정) + 소제목 전부 + 후보 표. 본문 전문은 주지 않는다.
  · 모델 출력은 {"core":[인덱스...], "new":[...]}. 범위 밖·본문에 없는 것은 버린다 (불변식).
  · 입출력 스키마는 코드가 소유한다. 모델 이름은 설정이다.
  · extractor_ver = 프롬프트 + 사전 + 매칭 방식. 발굴기 버전은 안 들어간다.
```

**경계 줄의 출처는 둘뿐이다.** ① 문서가 결정으로 표시한 것 — `pipeline-core.md` §3 불변식 · §2 확정 사항 · §5 파라미터(잠정값) · §4 seam 표의 *계약* 열. ② 다른 부품이 기대는 계약 — 테이블 컬럼·유일성 · 버전 규칙 · 재실행 멱등 · 다른 부품이 부르는 인터페이스. 둘 다 아니면 방법이다. 문서 서술 절의 "이렇게 한다"(원문 §3.2 어댑터 4종, §4.6 공통 어댑터·`mine()` 시그니처, §5.1 Aho-Corasick)는 문서가 그린 한 가지 방법이지 결정이 아니다. seam 표의 "바꿀 때 건드리는 것" 열도 방법이다. 이 부품 안에서만 끝나는 선택은 수행자 몫이다.

경계는 *선택지의 울타리*지 *방법*이 아니다. 울타리가 없으면 수행자는 어디까지가 자기 결정인지 모르고, 방법까지 적으면 자기 결정이 없어진다. **경계가 열 줄을 넘으면 방법이 섞인 것이다.**

**잠정값은 반드시 표시한다.** `pipeline-core.md` §5는 전부 초안이고 "데이터를 보고 정한다". 확정값처럼 적으면 나중에 바뀔 때 "왜 말 안 했냐"가 된다.

### 왜 줄 — 층마다 대상이 다르다

- **스토리 → 사용자.** 기능 한 조각이라 사용자 가치가 진짜 있다.
- **하위 작업 → 바로 다음에 이걸 쓰는 것.** 사용자까지 거슬러 올라가지 않고 한 칸만 간다.

사용자까지 끌고 가면 31개 이슈의 왜가 "사용자가 트렌드를 보려면"으로 전부 같아진다. **구별이 안 되는 정보는 정보가 아니다.** 한 칸만 가면 태스크마다 달라지고, 수행자가 실제로 쓸 수 있는 정보가 된다 — 내가 만든 걸 누가 어떻게 쓰는지 알면 인터페이스를 그쪽에 맞춘다.

재료는 문서에 있다. §3 불변식 표의 **"깨지면"** 열이 통째로 이 용도고, §2 매칭 설명이 이미 다음 소비자를 가리킨다.

```
[BE] 저장 계층 스키마 구축 — article/mention/extraction
왜   추출·집계가 전부 여기에 쓴다. 스냅샷이 남아야 재처리 때 다시 크롤링하지 않고,
     삭제된 기사도 잃지 않는다.

[AI] 주간 집계 구현 — 상위·급상승·신규 3종
왜   사용자가 보는 화면이 이것이다. 여기까지 와야 파이프라인이 산출물을 낸다.
```

## 7. 제목 — 사용자 관점은 제목의 일이 아니다

리서치 결론: **제목을 사용자 관점으로 쓰라는 건 통설과 어긋나고, 이 팀의 기존 관행이 맞다.**

- Mike Cohn — 백로그의 **약 85%만** 사용자 스토리로 굴러가고 **약 10%는 사용자가 어디에도 없어** 형식이 *"인위적이거나 우스꽝스럽게"* 느껴진다. 그런 항목엔 FDD feature 형식 `[동작] the [결과] of/for a(n) [대상]`을 권하며 *"백엔드 기능과 API에 특히 잘 맞는다"*고 한다.
- Lullabot — *"As the system, I want…"*는 **시스템에 욕망을 부여**한다. *"사용자에 대한 심상이 명백히 틀렸다면 또 무엇을 틀리고 있겠는가?"* 대안은 **"무엇을 해야 하는지를 선언하는 명령형 문장"**.
- Lullabot — 개발자 층위 작업은 **하위 작업(subtask)**으로 내린다. 사용자 스토리 형식은 **스토리 층에만** 적용되는 규약이다.
- Atlassian 커뮤니티 — 요약은 짧게(3~5단어). **보드 카드에서 잘리지 않아야** 스탠드업에서 쓸모가 있다.

이 팀 실제 관행이 이미 그렇다 — 스토리 24개 전부 짧은 명사구, "사용자는 ~할 수 있다"인 게 0건. (`jira-common/JIRA-GUIDE.md`가 그 형식을 권하지만 **이전 프로젝트 문서**고 이 프로젝트에선 아무도 안 따랐다.)

### 형식

**스토리** — 짧은 명사구. 사용자 관점은 **본문 첫 줄**로 내린다.

```
키워드 사전 구축
  랭킹에 오를 수 있는 말이 여기서 정해진다. 사전에 없는 말은 어떤 랭킹에도 못 오른다.

주간 트렌드 집계
  사용자가 보는 화면이 이것이다 — 상위·급상승·신규 세 랭킹.

공용 인프라 환경 구축
  수집·추출·집계가 전부 이 위에서 돈다.
```

**하위 작업** — `[파트] 부품 + 동사 — 안에 든 것`. 사용자 관점을 요구하지 않는다.

```
[DATA] 추출기 구현 — 프롬프트 계약·배치·extractor_ver, 3개월 전량 추출 포함
[DATA] 매체 어댑터 4종 구현 — 8개 매체, 3개월 백필 포함
```

**동사를 반드시 넣는다.** `[FE] 연관 키워드 그래프 UI`는 설계인지 구현인지 스타일링인지 모른다. 대시 뒤에는 이 부품에 흡수된 것을 적는다 — 합친 흔적이 제목에 남아야 "이게 왜 이렇게 크지"가 안 나온다.

### 접두어와 라벨이 어긋난 채로 둔다

`[DATA]` 접두어가 붙은 이슈에 `AI` 라벨이 달려 있다(`-8`, `-9`). 두 어휘가 같은 걸 다르게 부른다. **통일하지 않는다** — 통일하려면 기존 이슈를 고쳐야 하고 그건 이 스킬의 일이 아니다. 제목은 `[DATA]`, 라벨은 `AI`.

사람 이니셜 라벨(`hg` `ww`)은 안 붙인다. 담당자를 비우기로 했으니 앞뒤가 안 맞는다.

## 8. 검사 셋 — 둘은 같은 모양이라 접는다

| 검사 | 무엇을 보나 |
|---|---|
| **부품 검사** | 크기 — 테이블 경계를 넘나 / 남의 태스크 필요 / 경계에 방법이 섞였나 |
| **도구 검사** | 도구 이름·용어를 지워도 제목·완료 기준·경계가 멀쩡한가. 도구를 바꿔도 부품 이슈가 그대로면 할당 단위다. `[INFRA]` 만 예외 |
| **출처 검사** | 경계 줄마다 출처 — 결정 표인가, 다른 부품이 기대는 계약인가. 못 대면 방법. 도구 검사가 못 잡는 "공통 어댑터"·"함수 둘"을 잡는다 |
| 스토리 검사 | 첫 줄에서 "사용자"를 지워도 멀쩡하면 스토리가 아니다 (저장 계층이 여기 걸렸어야 했다) |
| 왜 줄 검사 | 다른 태스크에 갖다 붙여도 말이 되면 → 왜가 아니다 |
| 사용자 검사 | "사용자"를 지워도 멀쩡하면 → 사용자 관점이 아니다 |

**아래 둘은 같은 질문이다** — *이 줄이 이 이슈에만 해당하는가.* SKILL.md를 쓸 때 하나로 접는다(`writing-great-skills`의 leading word 원칙). 첫 번째는 크기를 보는 거라 별개로 둔다.

## 11. 재실행 — 완료된 것만 안 건드린다

`pipeline-core.md` §5 파라미터가 전부 초안이라 첫 실측 후 문서가 바뀌고, 그때 다시 부르게 된다.

라벨로 기존 이슈를 불러와 **제목으로 대조**하고 표를 먼저 낸다.

```
새로 생김      → 등록
그대로         → 건드리지 않음
본문 바뀜      → 갱신
문서에서 사라짐 → ⚠️ 표에만 올림. 자동으로 안 지운다
```

제목 대조는 정확하지 않다(제목을 고치면 "사라짐 1 + 새로 생김 1"로 보인다). 그래서 자동 처리하지 않고 **표로 보여주고 사람이 확정**한다.

### 규칙

**완료된 이슈만 안 건드린다. 나머지는 본문을 고치고 무엇이 왜 바뀌었는지 코멘트 한 줄.**

**완료 이슈에 영향이 가면 본문을 고치는 게 아니라 새 태스크를 만든다.** 완료된 일은 옛 명세대로 한 게 맞고, 다시 할 일이 생긴 거다. §3 불변식 6이 전량 재처리를 다루는 방식과 같다.

**아무것도 안 지운다.**

### "손 안 탄 것만 고친다"를 버린 이유 — 시뮬레이션

9/1 등록 → 스프린트 2에서 8개 진행 → 9/12 실측으로 문서 3곳 변경 → 재실행. 갱신 대상 4건 중 **2건이 막혔고, 막힌 둘이 지금 사람이 실제로 손대고 있는 것**이었다. 안전장치가 가장 필요한 곳에서만 꺼진다.

깨진 것 둘:

1. **이슈 본문이 영구히 거짓말을 한다.** 정정이 코멘트 4번째에 묻히고, 담당자는 그날은 알지만 다음 사람은 본문을 믿는다.
2. **"손 탔음"의 대리 지표가 부정확하다.** 코멘트는 **GitLab MR이 자동으로 붙인다**(`-70`이 실물 반례) — 연동을 켜는 순간 무의미해진다. 담당자는 선점만 해둔 경우가 있다. **상태만 정확하다.**

"진행 중인 사람 발밑에서 명세가 바뀐다"는 걱정은 남지만, **그건 문서가 바뀐 순간 이미 벌어진 사실이다.** 이슈를 옛 상태로 두는 건 사실을 감추는 것이지 막는 게 아니다. 빨리 알수록 손해가 적고, Jira가 본문 변경 이력을 남기니 되돌릴 수 있다.

```
skills/to-jira/
  SKILL.md
  references/        재실행 분기 등, 일부 실행만 읽는 것을 내린다
docs/design/
  to-jira-skill.md   이 합의문
```

`install.sh`는 저장소 경로를 `$BASH_SOURCE` 기준으로 잡으므로 **수정 없이 복사**하면 된다.

**왜 `claude-skills`에 넣지 않고 새 저장소인가** — 이 스킬은 팀 Jira 컨벤션에 묶여 있어 팀과 공유할 수 있다. `claude-skills`는 개인 것이다. 대가는 `install.sh` 한 벌이 복제되는 것인데, 그 파일은 저장소 이름에 의존하지 않아 관리 부담이 거의 없다.

## 14. 2026-09-02 재단 — 39건이 14건이 된 경위

첫 실행이 `pipeline-core.md` 에서 하위 작업 **39건**을 만들었다. 사용자 판정: *"하위 작업 단위로 branch 를 파서 시작해. 디테일하게 나누어져 있어서 여러 번 작업을 해야 돼. 구현을 어떻게 할지에 대해서도 나누어져 있어. 구현은 구현할 때 고민하고 여기서는 어떤 일을 할당할 것인가만."*

**원인은 옛 §5 였다.** "완료 기준 한 줄이 서는 **가장 작은** 덩어리" + "접속사로 판정이 둘이면 나눈다"를 구현 단계에 그대로 적용하면 "입력을 조립하고 출력을 검증한다"가 둘로 갈린다. 결과가 구현 분해도다. 규칙이 할당 단위가 아니라 테스트 단위를 겨냥하고 있었다.

**바꾼 것**

| | 전 | 후 |
|---|---|---|
| 단위 | 완료 기준이 서는 가장 작은 덩어리 | 브랜치 하나 = 부품 하나 (테이블·인터페이스로만 통신) |
| 접속사 | 나누는 신호 | 신호 아님. 다른 부품일 때만 |
| N개 집합 | 나누는 신호 | 같은 인터페이스 구현체가 여럿이면 ⚠️ 로 사람이 정함 |
| 실행 태스크 | 별도 (⚠️ 배치 단위) | 결과를 내는 부품의 완료 기준에 흡수 |
| 경계 | 없으면 헤매는 것 전부 | 설계 결정만 (불변식·seam 계약·잠정값). 열 줄 넘으면 방법이 섞인 것 |
| 크기 기준 | 없음 | 기존 하위 작업 하나 = 브랜치 하나 |

**사람이 정한 갈림길**: 어댑터 4종 → 1건 (8개 매체가 한 브랜치), 이어서 크롤러 공통 기반과도 합침 — "공통 기반을 어댑터 없이 먼저 만들 수 있나"라는 지적. 기반은 구현체가 있어야 인터페이스가 굳고 구현체는 기반이 있어야 돌아가는 양방향 의존이라 한 브랜치가 맞다. `pipeline-core.md` §8 순서 줄도 같이 고쳤다. 실행 3건 → 부품 완료 기준에 흡수. 저장 계층(스토리 96·하위 작업 105)도 같은 이유로 지웠다 — 테이블의 주인은 그걸 처음 쓰는 부품이고, 소비자 없는 스키마 브랜치는 컬럼 없는 DDL 이 된다. 접속 계층·DDL 적용 틀·표준 SQL 규약은 크롤러가 만든다. 스토리의 사용자 줄도 없었다("모든 부품이 여기 쓴다"는 사용자가 아니다). 경계는 설계 결정만, 문서 참조 없음 유지. Jira 반영은 키 재사용(편집) + 잉여 25건은 사람이 삭제 (MCP 에 삭제 도구 없음).

**Airflow 채택 (같은 날)**: 오케스트레이션이 Airflow 로 정해지자 서버화 스토리 104·하위 작업 142 가 사라졌다 — 스케줄·재시도·배치 대기가 Airflow 몫이라 각 부품이 자기 DAG 를 갖는다. 대신 `[INFRA] Airflow 구성` 이 스토리 97 아래 새로 생겼고 첫 DAG(수집 백필)보다 앞선다. SQLite 로컬 검증과 "표준 SQL만" 제약도 버렸다 (Airflow 가 PostgreSQL 을 띄운다). 부품 7건(107·125·128·130·135·139·141)은 문구만 바뀌었다.

**도구 어휘 되돌림 (같은 날)**: Airflow 를 반영하며 부품 7건의 제목·완료 기준·경계에 DAG·센서·XCom·short-circuit·trigger 를 써 넣었다. 사용자 지적: *"구현이 바뀌었다고 하위 작업과 스토리가 바뀌는 것이면 구현에 얽매여 있던 거 아닐까?"* 부품 11개는 Airflow 전후로 그대로였으니 단위는 도구와 무관했지만, 문구가 도구에 묶였다. 도구를 Prefect 로 바꾸면 7건을 또 고쳐야 하는 상태였다. 도구 무관 문구로 되돌리고 **도구 검사**를 셋째 검사로 추가했다. 남긴 것은 도구 무관한 설계 결정 — 멱등 · 제출과 수거는 다른 실행일 수 있다 · 재처리는 새 ver 로 쌓고 마지막에 원자적으로 바꾸며 현재 ver 포인터가 필요하다 · 주기. 서버화 스토리가 사라진 것은 도구가 아니라 설계 문서의 "로컬 v1 → 서버화" 국면 구분에 묶여 있던 것이라 그대로 둔다. `[INFRA] Airflow 구성` 은 인프라라 도구 이름을 단다.

**방식 되돌림과 출처 검사 (같은 날)**: 사용자 지적 — *"도구 검사가 특정 방식이나 그런 것도 포함되는 거야? 하위 작업이 너무 세세하게 되어 있다거나, 공용-어댑터 방식을 미리 상정하여 구현 세부까지 미리 정의하였다거나 하는 문제도 있었어."* 도구 검사는 도구 이름만 잡고 방식은 못 잡는다. 근본 원인은 설계 문서가 결정(표)과 방법(서술)을 섞어 두고 스킬이 구분 없이 옮긴 것이다. 그래서 **출처 검사**(경계 줄마다 결정 표 또는 부품 간 계약이라는 출처를 댄다), **부품 수 상한**(단계 + seam 의 두 배), **스토리 검사**(사용자 줄), 점검 흔적의 **"방법으로 뺀 것"** 줄을 추가했다. 107 에서 "어댑터 4종·매체당 함수 둘", 116 에서 "공통 어댑터·`mine()` 시그니처", 135 에서 단계 순서를 뺐다. 스킬이 못 하는 것: 결정 표에 든 것이 정말 결정인지는 문서 저자만 안다 — 그래서 4단계 승인이 남는다.

**결과**: 스토리 **7** (96 저장 계층·104 서버화 삭제) + 하위 작업 **12** (Airflow 구성 · 107 · 116 · 119 · 122 · 125 · 128 · 130 · 135 · 136 · 139 · 141). `Blocks` 링크는 부품 사이 14개.

**남는 긴장**: 자족성("팀원은 문서를 안 본다")과 "방법은 적지 않는다"가 맞닿는다. 컬럼 초안·사이트맵 경로 같은 세부는 이제 이슈에 없다. 구현 때 설계 문서를 여는 걸 전제로 한다 — 문서 참조는 여전히 안 적지만, 문서 라벨로 되짚을 수 있다.
